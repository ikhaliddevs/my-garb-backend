## Refined validation and business rules

- Submission fields: designerId (24 hexadecimal characters), outfitType (1-100 trimmed characters), description (1-4000), quantity (integer 1-100), desiredCompletionDate, budgetAmount, optional referenceImageUrls (0-5 distinct validated external HTTPS references), and shareMeasurements (must be true). Reject unknown fields, control characters, object/query injection and supplied participant/status/snapshot fields. POST creates a new request each time; submission is not an idempotent operation.
- A new request targets an active designer with completed M3 discovery eligibility. Availability is informational and does not independently prohibit requests. Read the customer's current private measurement set server-side: require 1-50 named positive values, existing M3 label/value bounds and unit cm/in; copy the entire set with capturedAt into an immutable submission snapshot. No inline measurements or arbitrary owner IDs. Explicit shareMeasurements=true authorizes sharing that set only with the selected designer. Missing/empty measurements cause 409 MEASUREMENTS_REQUIRED. Later private edits do not affect either snapshot.
- Money is NGN only: budgetAmount and accepted proposal priceAmount are decimal strings, 0.01 through 100000000.00, with at most two fractional digits, no signs/exponents/commas/leading zeroes except zero before a fraction. Store integer kobo (1 through 10000000000); return canonical two-decimal amount strings and currency NGN. No floating-point money storage, payments or paid flag.
- Dates are real calendar dates in YYYY-MM-DD, interpreted as UTC calendar days. On submission/acceptance they must be strictly after today's UTC date and no more than 730 days ahead. A proposal can differ from the requested date; the customer explicitly confirms its price/date. First confirmation rechecks that the proposed date is still in the future. Retrying an already committed confirmation is allowed even after that date, to recover the same order.
- PATCH /requests/:id/decision: decision=accepted or declined and nonempty responseText (1-2000 trimmed characters) are required for both. Acceptance additionally requires priceAmount and completionDate; decline must not include either. Only the assigned active designer may decide a submitted request. PATCH cancellation is owning-customer only from submitted/accepted; cancelled/declined are terminal. No proposal edits or negotiation revisions in M4.
- GET lists/details are restricted to the current active participant with its corresponding customer/designer role; admins and unrelated users cannot access these APIs. Lists use page 1-1000, limit 1-50 (default 20), optional strict status filters, stable ID order and bounded database time. List summaries omit measurement values and description/reference details; participant details expose the agreed snapshots, never account contact/session/hash fields.
- Order states: confirmed -> in_progress -> ready by assigned designer, then completed by owning customer. Store each actor/time. Same-state retries are idempotent and add no history; backward/jump transitions fail. Customer confirmation creates the initial confirmed event. No order before confirmation.

## Standalone MongoDB confirmation and recovery design

The request document is the authoritative confirmation intent. Request/order writes use acknowledged journaling (w:1, j:true). The owning active customer atomically changes accepted -> confirmed with a status/date predicate and records confirmedAt/confirmedBy. Order ID is predetermined as the request's ObjectId (in the separate orders collection), with a unique requestId index. Freeze the accepted proposal and request snapshot; no endpoint edits either afterward. Before the first claim verify the assigned designer is still active; recovery of an already committed intent does not depend on later changes to that designer.

After the intent commits, idempotently upsert the order using requestId and $setOnInsert, copying only frozen request/participant/proposal/snapshot values and the original confirmation event. Unique requestId and deterministic _id prevent concurrent retries producing extra orders. Handle duplicate-key races by reading the one existing order. Concurrent cancellation/confirmation compete on the request status: only one wins. A failed/declined/cancelled claim must never create an order.

If order creation fails after intent commits, keep the confirmed request and return sanitized 503 CONFIRMATION_PENDING. Never roll it back or allow cancellation. GET request detail exposes orderId and orderPending; retry PATCH /requests/:id/confirm with {} completes the same durable intent, including after process restart. No in-memory locks, multi-document transactions, or dependency on process-local state. A lost response after successful insertion also returns the same order on retry. Order lists show only materialized orders; this temporary gap and explicit retry recovery are documented. There is no background recovery worker in M4. Tests must inject failures before/after order insertion, recreate the service/process and verify one unchanged order/event, as well as cancellation/confirmation and status-update races.
