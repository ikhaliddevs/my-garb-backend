# M4 requests, shared snapshots and orders

Implementation scope approved 1 November 2026. Branch: `feature/milestone-04-requests-orders`, from updated develop at `b2f9498fd1881f68b420440302d657577862f14e` (merged M3 PR #4). No PR creation/merge, main modification or M5 implementation is authorized. Manual verification is **PENDING**.

Local automated checks passed using an isolated verification copy: clean install/lint, 52 integration tests passed with one Windows signal skip, and 98 Postman requests / 251 assertions with zero failures (M4: 55 / 125). Publication and exact-head CI evidence are recorded in the test report and final handoff. Current audit: zero production findings; 23 unresolved development entries (11 high, 12 moderate, no critical).

The [refined M4 contract](M4-codex-prompt.md) implements PRD FR04-FR06: structured customer requests, explicit sharing of a nonempty saved measurement snapshot, required designer response text and proposed NGN price/date, pre-confirmation cancellation, customer confirmation, and participant-only orders with sequential actor/time history. Measurements remain immutable; corrections are explicitly deferred to the later messaging milestone.

Request confirmation stores a durable intent atomically before idempotent order materialization. Request/order writes require journal acknowledgement (w:1, j:true). A deterministic order ID and unique requestId prevent duplicates under retries/concurrency on standalone MongoDB. Failures after intent return sanitized 503 CONFIRMATION_PENDING; retrying the same confirm endpoint recovers the same order, including after process restart. Already completed production/history is never reset by confirmation retries. There is no background recovery worker or rollback to accepted after intent. A pending intent temporarily has no entry in the order list; request detail exposes orderPending.

All routes reuse cookie sessions, active-account/role checks, CSRF/CORS, 16 KB bodies, safe envelopes/logging and centralized errors. Detail endpoints restrict records/snapshots to participants; list projections omit measurement values and large private details. Unknown fields/owner selectors, invalid money/dates, status jumps and unauthorized transitions fail. Money is stored in integer kobo and returned as exact NGN strings. No new package or environment dependency is required. Startup explicitly creates request/order indexes; imports do not connect/listen, and no transaction/replica-set assumption is introduced.

Deliverables include OpenAPI 0.4.0, an **M4 Requests and Orders** folder in the existing tracked main Postman collection (prior scripts retained), blank M4 manual environment, [manual guide](../postman/M4-guide.md), regression/security/recovery tests, [test report](M4-test-report.md), local ignored AGENTS.md updates, and a prepared [M5 prompt](M5-codex-prompt.md). The user's external edited Postman collection is not overwritten; copy only the new folder and its scripts. Automated M1/M2, M3 and M4 folders use separate test API instances/cookie jars without weakening rate limits.

Limitations: submission POST retries create additional requests; only confirmation and same-state order updates are idempotent. Availability is informational; an active M3-eligible designer may receive a request regardless of the availability flag. Monetary/date/measurement bounds and empty-measurement rejection are explicit implementation decisions in the refined contract. No proposal revisions, measurement amendments, messaging, notifications, payments, administrative views or post-confirmation cancellation are implemented. Human/manual testing, residual development dependency risks and latest-SHA CI status must be read from the test report, not inferred from implementation alone.
